**Findings**

1. [P1] The orchestrator runs every remaining plan step at once, which inflates peak RAM and defeats incremental reasoning. In [orchestrator.py (line 448)](app://-/index.html?hostId=local#), steps_to_run is the entire tail of the plan, then [ThreadPoolExecutor(max_workers=len(steps_to_run)) (line 460)](app://-/index.html?hostId=local#) executes them all before any state is committed. Each worker can do a 60-result vector/hybrid retrieval, rerank, and then full-file expansion in [supervisor.py (line 96)](app://-/index.html?hostId=local#) and [supervisor.py (line 196)](app://-/index.html?hostId=local#). That means the peak resident set is the sum of all step payloads, not one step’s payload. It also means every reflect() call sees the same stale past_steps snapshot, so the “reflection loop” is not actually pruning later work; it just parallelizes redundant work.
2. [P1] Full-content expansion is the largest memory amplifier and it is applied too early and too broadly. [execute_step() (line 198)](app://-/index.html?hostId=local#) expands every post-rerank vault/hybrid result, and [_expand_full_content() (line 317)](app://-/index.html?hostId=local#) replaces snippet-sized content with full file text in place. With defaults, that is up to 20 docs per step, each potentially up to 100 KB for non-mlx providers. The same file can be re-read on repeated hits across steps because there is no cache keyed by filepath/mtime. The result is a state full of full documents even though the final prompt only consumes a small bounded subset.
3. [P2] The same evidence is retained in too many shapes, and most of it is redundant. The state model already stores past_steps, accumulated_context, retrieved_documents, and raw_context_buffer in [state.py (line 17)](app://-/index.html?hostId=local#). The query loop appends full docs to retrieved_documents, truncated copies to raw_context_buffer, and another textual summary to accumulated_context in [orchestrator.py (line 465)](app://-/index.html?hostId=local#). Later, the reflector, planner extension, and policy each serialize that history again into prompt strings in [reflector.py (line 41)](app://-/index.html?hostId=local#), [planner.py (line 125)](app://-/index.html?hostId=local#), and [policy.py (line 29)](app://-/index.html?hostId=local#). Since the synthesizer prefers raw_context_buffer whenever it exists in [synthesizer.py (line 117)](app://-/index.html?hostId=local#), most of retrieved_documents is being kept alive mainly for source rendering.
4. [P2] The source-merge path does an expensive full pass over all retained docs and can then do it again after a second web fetch, without re-synthesizing the answer. [_build_structured_sources() (line 215)](app://-/index.html?hostId=local#) walks every doc, normalizes scores, and runs _clean_snippet(doc.get("snippet") or doc.get("content")) in [orchestrator.py (line 234)](app://-/index.html?hostId=local#), so if content was fully expanded it rescans large strings just to emit 12 sources. Then the orchestrator may perform a fallback web retrieval before synthesis in [orchestrator.py (line 530)](app://-/index.html?hostId=local#) and another final web retrieval after synthesis in [orchestrator.py (line 594)](app://-/index.html?hostId=local#). That last pass updates sources but not answer, so the source list can contain evidence the model never saw.
5. [P2] The planner has a format mismatch that can force overly broad fallback retrieval. In [planner.py (line 49)](app://-/index.html?hostId=local#) and [planner.py (line 141)](app://-/index.html?hostId=local#), the prompt asks for a JSON array, but both calls request response_format={"type": "json_object"} in [planner.py (line 89)](app://-/index.html?hostId=local#) and [planner.py (line 153)](app://-/index.html?hostId=local#). On stricter providers that increases parse-failure risk, which drops into the single-step hybrid fallback in [planner.py (line 111)](app://-/index.html?hostId=local#). That fallback is one of the highest-volume retrieval modes in the stack.
6. [P3] There are smaller but persistent churn patterns: repeated sum(...) over the entire raw buffer on every append in [orchestrator.py (line 474)](app://-/index.html?hostId=local#) and [orchestrator.py (line 550)](app://-/index.html?hostId=local#), plus repeated large-string concatenation in the synthesizer in [synthesizer.py (line 109)](app://-/index.html?hostId=local#). These are not the primary RAM issue, but they add avoidable CPU churn.

**Overall assessment**

The biggest problem is not one bad data structure; it is the pipeline shape. The system eagerly broadens retrieval, eagerly expands full files, retains the expanded payload in long-lived state, then reserializes the same evidence multiple times for reflection, planning, policy, synthesis, and source formatting. The source merge logic is also decoupled from synthesis badly enough that it can add post-hoc sources the answer never used.

If I were fixing this, I’d do it in this order:

1. Change the orchestrator to execute one plan step at a time, or at most bounded concurrency for explicitly independent step groups.
2. Replace retrieved_documents with lightweight source records plus lazy content refs; only expand full text for the small set selected for synthesis.
3. Cache expansions by filepath and mtime, and never expand the same file twice in one query.
4. Build final sources from lightweight snippets only, and remove the post-synthesis web-fetch path unless synthesis is rerun.
5. Fix the planner response format mismatch and add tests for multi-step plans, repeated-source hits, and final-source consistency.
